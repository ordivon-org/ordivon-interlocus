# Ordivon Network Operational Realization Theory v0

Status: PROVISIONAL DERIVED THEORY / ROUND-1 SURVIVOR

Upstream authorities:

- frozen `NCT_v1=<K,Π,H;J>_Γ`;
- frozen Network Capability Calculus v1;
- frozen Network Projection & Currentness Theory v1.

This theory defines the H-side semantic carrier for Network-owned realization history. It does not turn Network into a universal execution/process owner.

## 1. Minimal event object

A Network realization event is:

`η=<eid,eventRole,subjectRole,subjectIdentity,ownerRole,epoch,preRefs,postRefs,resourceDelta,timeEnvelope,bridgeRefs,provenance>`

where:

- `eid` — immutable occurrence identity;
- `eventRole` — typed Network realization role;
- `subjectRole/subjectIdentity` — Network-facing subject transformed/related by the event;
- `ownerRole` — semantic owner of the event predicate; Network-owned events and foreign bridge events remain distinguishable;
- `epoch` — realization/claim/contract lineage epoch relevant to the event;
- `preRefs/postRefs` — references to required/provided Network support, K clauses, Π projections or external-owner facts, not copies of their owned semantics;
- `resourceDelta` — typed usage/resource transformation witness where applicable;
- `timeEnvelope` — occurrence interval/ordering constraints rather than a universal timestamp scalar;
- `bridgeRefs` — external Harness/Runtime/World/Host/etc. event/receipt references used as premises or consequences;
- `provenance` — evidence/lineage sufficient to interpret the occurrence.

An event may record a Network occurrence without claiming a Runtime Attempt or world effect.

## 2. Realization History Graph

A history is a typed graph:

`H=<hid,V,≺c,≺d,#,Λ,B,T,P>`

where:

- `V` — immutable realization events;
- `≺c` — causal/realization precedence relation;
- `≺d` — support/dependency precedence relation when distinct from causality;
- `#` — typed conflict/exclusion relation for mutually exclusive branch occurrences where admitted;
- `Λ` — lineage/transformation/migration edges between subject identities/epochs;
- `B` — branch/cohort/race membership and selector-result annotations;
- `T` — temporal constraints/interval relations;
- `P` — provenance/evidence references and owner-bridge ledger.

For a materialized finite history, `≺c` is acyclic. A state, topology, provider or binding may revisit a previous-looking value, but the occurrence events are new identities.

Canonical laws:

`StateRevisit != HistoricalCycle`.

`SerializationOrder != CausalOrder`.

`TemporalPrecedence != Causality`.

`ObservedAfter != CausedBy`.

## 3. Event roles

Network-native realization roles may include:

- `ESTABLISH` / `EXPOSE` / `REVOKE`;
- `TRANSFORM` / `REFINE` / `SPLIT` / `MERGE` / `CONSUME` / `RESERVE`;
- `WAIT` / `STORE` / `CARRY`;
- `DISCOVER` / `RESOLVE` / `BIND` / `REBIND`;
- `FORWARD` / `DELIVER_NETWORK_OUTCOME`;
- `BRANCH_OPEN` / `BRANCH_RESOLVE` / `FAILOVER`;
- `INVALIDATE` / `DEGRADE` / `REPAIR` / `RECOVER`;
- `MIGRATE_CONTRACT` / `MIGRATE_CLAIM_EPOCH`;
- `RECONCILE` / `COHORT_MERGE`;
- `ACQUIRE_EVIDENCE` / `UPDATE_EVIDENCE_REFERENCE`.

This list is a typed family, not a universal state-machine enum. Specializations may refine roles without creating new Network Foundations.

## 4. Proposal / attempt / occurrence / effect / outcome / evidence separation

Keep the following roles distinct:

### Proposal / intent

A Harness/Host/operator plan, selection or request to realize something.

### Admission / Attempt

Runtime/owner-specific operational commitment and physical attempt semantics. Network may carry a bridge reference but does not own generic Attempt truth.

### Network occurrence

A Network-owned realization event such as binding established, packet forwarded under a forwarding specialization, capability exposed, member failover selected, resource transformed, or recovery relation established.

### External effect

A World/Runtime/domain-owner fact resulting from physical action. It may support or be required by a Network occurrence but is not generated by Network notation.

### Network outcome

A Network-facing result/projected consequence of one or more events, e.g. delivered network outcome, established binding, unavailable branch, recovered relation.

### Evidence

Observation/receipt/provenance supporting occurrence/effect/outcome claims; governed by Projection & Currentness Theory.

### Satisfaction

K/J evaluation of whether the realization/outcome satisfies a requirement.

Canonical separations:

`Proposal != Admission != Attempt != NetworkOccurrence != ExternalEffect != NetworkOutcome != Evidence != Satisfaction`.

`NoEffect != NoOccurrence`.

`UnknownEffect != NoEffect`.

`Failure != NoHistory`.

## 5. Foreign bridge events

A foreign-owner event enters H as:

`BridgeEventRef=<owner,eventId,eventRole,claimScope,receipt/evidenceRef>`

plus an explicit bridge rule describing which Network transition it can induce.

Examples:

- `HarnessSelect(A)` may induce a Network continuity/claim-epoch transition;
- `RuntimeAttemptSucceeded(r)` may support a Network occurrence only where the Network bridge contract proves the relevant relation;
- a World physical-support change may invalidate a Network capability relation;
- Host recovery/currentness facts may constrain a research/operational continuation projection without becoming Network history ownership.

Canonical laws:

`ForeignEventReference != NetworkOwnership`.

`BridgeEvent != ImportedOntology`.

`RuntimeAttempt != NetworkRealizationByIdentity`.

## 6. Partial order and serialization

H is not defined by one total log order.

A total serialization may be materialized for storage/debugging, but it is only a projection if it orders events that are causally independent.

`Serialize(H)=>L` requires retaining which order relations are semantic (`≺c`, `≺d`, T constraints) and which are arbitrary tie-breaking.

Canonical laws:

`LogOrder != HappensBefore`.

`ConcurrentEventsNeedNotBeOrderedSemantically`.

`TotalOrderProjection != TotalOrderOntology`.

## 7. Resource-transforming histories

Where K usage semantics declares a resource/capability usage theory, an event may carry:

`Δr_η: R_in --[w]--> <R_out,R_residual>`.

No universal conservation, duplication or linearity law is assumed.

Examples may include:

- consumable relational resources;
- reservable/exclusive capacity;
- reusable service capability;
- split/merge transformations;
- transformation that produces a new capability identity from consumed supports.

Canonical laws:

`ResourceTransformationRequiresWitness`.

`Transformation != Duplication`.

`Consumption != HistoricalErasure`.

`OutputCapabilityIdentityRequiresTransformationLineage`.

## 8. Wait / store / carry

Wait and persistence intervals are first-class history, not identity operations.

`WAIT(Δt)` may change:

- K deadline/freshness/lifetime residuals;
- Π/J currentness;
- opportunity/contact availability;
- custody/storage obligations;
- branch eligibility;

while leaving some structural support projection unchanged.

`STORE` and `CARRY` may preserve a payload/resource/obligation across an interval while topology/serviceability changes.

Canonical laws:

`Wait != Identity`.

`NoForwardingDuringInterval != NoRealizationHistory`.

`TemporalEvolutionCanChangeStandingWithoutTransfer`.

This accommodates delay/disruption-tolerant realization without making a contemporaneous end-to-end path universal.

## 9. Forwarding specialization

Forwarding history is one typed specialization:

`H_fwd ⊂ H`.

A forwarding event may include packet/flow/cohort identity, ingress/egress relation, forwarding decision, local state/version, dependency/support and evidence references.

Forwarding-specific causal traffic lineage remains preserved, but non-forwarding realization families are not forced into forwarding semantics.

`Reachability != ForwardingOccurrence`.

`ForwardingOccurrence != DeliveryOutcome`.

## 10. Branch / race / failover history

A race/failover realization records more than the winner.

A branch cohort may include:

- eligible alternatives at decision time;
- selector/decision owner reference;
- branch activation/open events;
- winner/selected branch;
- loser/cancelled/failed branch outcomes where observable;
- shared dependencies;
- timing/latency evidence;
- failover lineage and prior active identity.

Canonical laws:

`Winner != WholeRaceHistory`.

`LosingBranch != NonOccurrence` when a branch was actually attempted/activated.

`Failover != FreshUnrelatedSelection` unless lineage says so.

`AlternativeCount != IndependentHistory`.

## 11. Retry / replay / continuation / repair / recovery / reconciliation

These are distinct history relations.

### Replay

Re-presentation/re-consumption of the same exact recorded request/input/event reference. Whether replay produces a fresh physical attempt or returns historical support belongs to the relevant owner contract.

### Retry

A new realization/attempt opportunity directed at a still-relevant goal/requirement after prior failure, timeout or uncertainty. Retry has a new occurrence identity unless an external owner explicitly proves exact replay identity semantics.

### Continuation

Extension of an existing admitted association/history identity under a continuity witness.

### Repair

Transformation of support/configuration/binding/dependency conditions intended to make a previously blocked/degraded realization admissible again.

### Recovery

An H relation establishing an admissible post-failure continuation/standing, possibly preserving selected identities and changing others.

### Reconciliation

Evidence/history operation that determines which standing/effects/obligations remain after ambiguity, divergence or recovery; may trigger later repair/compensation/retry.

Canonical laws:

`Retry != Replay != Continuation != Repair != Recovery != Reconciliation`.

`RetryDoesNotErasePriorAttempt`.

`RecoveryRequiresLineageWitness`.

`Recovery != RetroactiveSuccess`.

`Reconciliation != Undo`.

`UnknownOutcomeRequiresReconciliationBeforeUnconditionalConsequentialRepeat`.

The final rule is scoped to Network consequential repetition; Runtime owns generic execution retry/effect policy.

## 12. Failure and partial outcomes

Failure is itself part of history when an occurrence/attempt/transition was made or a required relation became invalid.

A history may end in:

- positive Network outcome;
- negative outcome;
- partial outcome;
- unknown outcome;
- degraded standing;
- residual K obligations;
- recovery/reconciliation requirement.

`FailedHistory != EmptyHistory`.

`PartialOutcome != NoOutcome`.

`UnknownOutcome != FailedOutcome`.

Satisfaction remains a J/K judgement and is not inferred directly from occurrence count.

## 13. Compensation / reconciliation

A later compensating or reconciling event does not delete the earlier event/effect from history.

`Compensate(η1)=>η2`

means η2 establishes a new state/standing intended to offset or reconcile consequences of η1 under an owning contract.

Canonical laws:

`Compensation != Erasure`.

`Reconciliation != HistoryRewrite`.

`NetEquivalentState != SameHistory`.

## 14. Contract and claim migration

H carries the transition witness for:

`K_v --[h,w]--> K_v'`

and:

`ck_ε --[h,w]--> ck_ε'`.

H does not decide K semantics or Projection/Currentness authority. It records the admitted event/lineage by which those identities changed.

`MigrationEvent != SemanticEquivalenceProof`.

`MigrationDoesNotCarryStandingByDefault`.

## 15. History composition

Core composition is graph composition:

`ComposeH_Γ({H_i},W_h)=>H_res`

where `W_h` explicitly glues event identities/subjects/lineages and validates:

1. event identity noncollision or explicit same-event proof;
2. causal acyclicity;
3. dependency/support compatibility;
4. branch/conflict semantics;
5. resource transformation accounting;
6. epoch/version/identity migration compatibility;
7. foreign-owner bridge admissibility;
8. provenance retention.

Sequential, concurrent, branch/race, recovery and migration compositions are derived patterns.

No unconditional monoid is claimed.

`HistoryComposition != LogConcatenation`.

`ConcatenableLogs != ComposableRealizations`.
